# 기존 카테고리 정리

2026-09-30 결정. 기존 카테고리(`categories`, `posts.category_id`, 메뉴 CATEGORY 연결, POSTS 블록의 `category` 방식)를 콘텐츠 분류(유형·기수·주제)와 페이지로 대체한다. 순서는 **새로 쓰지 않기 → 기존 참조 이관 → UI에서 숨기기 → 충분히 안정화한 뒤 제거**다. 이관을 마칠 때까지 카테고리 테이블·컬럼·API는 삭제하지 않는다.

- 분류(유형·기수·주제)가 글의 정보이고, 페이지는 분류 조건으로 글을 모아 보여 준다. 한 글이 여러 모음 페이지에 나올 수 있다.
- 콘텐츠 모음은 새 페이지 타입이 아니라 일반 Page + POSTS(query) 블록이다.
- 메뉴는 PAGE 또는 직접 링크를 가리킨다.

## 1. 새로 쓰지 않기 (적용)

- **메뉴**: `SiteService.menu`가 새 CATEGORY 연결을 거부한다. React와 기존 Thymeleaf 화면 모두에 적용된다. 이미 CATEGORY를 가리키는 메뉴만 같은 대상을 유지한 채 이름·표시·순서를 편집하거나 페이지·링크로 바꿀 수 있다. 다른 카테고리로 바꾸거나 PAGE/LINK 메뉴를 CATEGORY로 바꾸는 것도 거부한다. React 메뉴 편집기는 새 연결 대상으로 페이지·직접 링크만 보여 주고, 기존 CATEGORY 메뉴에는 "이관 대상" 안내를 표시한다.
- **콘텐츠 모음 페이지 프리셋**: 전체 페이지 현황 → `＋ 새 페이지` → "콘텐츠 모음 페이지"에서 유형(필수)·기수·주제(선택)·표시 개수를 고르면, 조건 방식 POSTS 블록 하나가 들어간 임시보관 페이지를 기존 `POST /admin/pages/save-json`으로 만든다. 새 DB 타입·API는 없다. 제목은 "6기 프로젝트 후기"처럼 제안하며 바꿀 수 있다. 새 글은 게시되는 즉시 목록에 나오고, 조건을 바꾸면 페이지를 다시 게시해야 한다.
- 검증: 서버 전체 테스트 185개 실행, 실패 0, 환경 조건 제외 6. 프런트 테스트 67개. 메모리 DB `design-preview`에서 프리셋으로 만든 페이지에 POSTS query 블록(후기·최신순 6개)이 들어가고 편집기가 "조건으로 불러오기"로 여는 것, 새 메뉴 대상에 카테고리가 없는 것을 확인했다. 미리보기에는 카테고리와 CATEGORY 메뉴가 없어, 기존 메뉴의 "이관 대상" 표시는 브라우저로 보지 못했고 서버 규칙은 통합 테스트로 확인했다.

## 2. 공지사항: `GENERAL_NOTICE` (등록 전)

| 항목 | 값 |
|---|---|
| 주제 코드 | `GENERAL_NOTICE` (기존 `REVIEW_LIFE`, `FAQ_CLASS`와 같은 `<유형>_<이름>` 규칙) |
| 표시명 | 공지사항 |
| 정렬 | 20 (후기 0~2, FAQ 10~16 다음) |
| 허용 유형 | GENERAL만 |

별도 NOTICE 유형은 만들지 않는다. 등록은 스키마 변경 없이 `topics` 1행과 `content_type_topics` 1행을 넣는 **운영 데이터 작업**이다. 주제 사전 편집 화면이 없으므로 승인 후 정상 종료·백업·사본 검증을 거쳐 적용한다. 분류 검증과 편집기의 주제 선택은 사전을 그대로 읽으므로 코드 수정이 필요 없다. 기존 GENERAL 글 9건은 주제가 선택 사항이라 영향이 없다. 콘텐츠 작업 사이드바의 섹션(후기·FAQ·맛집)은 코드에 고정돼 있어, "공지사항"을 사이드바에 보이려면 프런트 수정이 필요하다. 주제는 삭제 기능이 없고 비활성화만 한다.

## 3. 기존 카테고리 조사 (읽기 전용, 자동 매핑 없음)

조사 원본: 정상 종료 상태로 보관 중인 V12 개발 DB의 임시 사본(14:31 상태, 조회 후 삭제). 카테고리·글·발행본·페이지 테이블은 RC1과 같다. **메뉴는 RC1에서 전환 뒤 바뀌었으므로** 이관 전에 RC1 정상 종료 기록으로 다시 확인한다.

| 카테고리 | 글 | 발행본 | 메뉴 | 페이지·템플릿 블록 | 결정 |
|---|---|---|---|---|---|
| #1 공지사항 | 0 | 0 | 2개(#34, #65, 둘 다 "공지사항") | 0 | GENERAL + `GENERAL_NOTICE`. 메뉴는 "공지사항" 모음 페이지로 교체(이관 때) |
| #2 교육 소식 | 1(#33, GENERAL, 임시보관, 주제 없음) | 0 | 0 | 0 | 새 주제를 만들지 않는다. #33은 GENERAL·주제 없음을 유지하고, `category_id`는 이관 때까지 그대로 둔다 |
| #33 카테고리1 | 0 | 0 | 0 | 0 | 대응 없음. 이관 단계에서 숨김 |

휴지통의 카테고리 글 0건. 과거 글 버전 1건에 카테고리 번호가 남아 있으며 이력으로만 읽는다.

## 4. 페이지 65(인사교 소개)의 category 방식 POSTS 블록 (변환 전)

- 위치: **임시보관본에만** 있다(페이지 revision 17). 공개본(revision 5, 2026-09-27 게시)에는 이 블록이 없고 HERO 블록 하나뿐이다. 공개 API `GET /api/public/v1/pages/65`로 확인했다. 지금 방문자에게 보이는 결과는 없다.
- 현재 의미: `sourceMode:"category"`, `categoryId:null` → 유형과 무관하게 **게시된 모든 글**을 최신 게시순 6개 보여 준다(`PublishedPostQueryService`, `CmsMapper.publicPosts`). 블록에는 쓰이지 않는 조건 값(`query: 후기, 6개`)이 함께 저장돼 있다.
- 조건 방식(query)은 유형을 반드시 하나 골라야 하므로 "모든 유형"을 **같은 의미로 옮길 수 없다.**
- 변환안(선택 필요)
  1. 저장된 조건 그대로 query로 바꾼다 → "후기" 최신 6개만 보이도록 의미가 바뀐다.
  2. 페이지 목적에 맞는 유형·기수·주제로 새 조건을 정해 바꾼다.
  3. 공개본에 없는 블록이므로 이관 단계까지 그대로 두거나, 필요 없으면 초안에서 뺀다.
- 참고: 공개본의 HERO 블록 링크가 `http://127.0.0.1:8081/admin/pages/65/edit`(관리자 주소)이고 문구는 "테스트"다. 운영 공개 전에 확인이 필요하다.

## 남은 단계

1. `GENERAL_NOTICE` 등록(승인된 운영 데이터 작업)
2. "공지사항" 모음 페이지 생성 → CATEGORY 메뉴 #34·#65를 그 페이지로 교체(중복 메뉴 정리 여부 결정)
3. 페이지 65 블록 변환안 결정
4. 카테고리 UI 숨김(콘텐츠 목록 필터, 사이드바의 기존 카테고리 연결, `LegacyLink` "기존 카테고리 관리")
5. 안정화 뒤 카테고리 테이블·컬럼·API·공개 API `categoryId` 조건 제거(별도 migration과 승인)
