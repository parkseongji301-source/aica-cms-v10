# 원본 migration 전 재확인 항목

이 기록은 4A 블록 기반 기능과 별개다. 원본은 V3를 유지하며 V4~V8 적용 승인을 의미하지 않는다.

## 1. 파일 DB 연결 수명

3C-1에서 실제 V3 파일 사본의 Flyway 호출이 짧은 연결로 연속 실행될 때, 두 번째 migrate가 0 대신 3을 보고한 현상이 두 번 재현됐다. 원본 DB나 migration SQL을 변경하지 않았다. H2/Flyway/Windows 파일 환경 중 정확한 내부 원인은 확인되지 않았다.

검사는 Hikari 실행 환경처럼 연결을 유지한 동안 migrate 3 → 재실행 0을 확인하고, 연결을 완전히 닫은 후 새 Flyway에서도 V6와 재실행 0, 기존 데이터 전체 동일성을 검사하도록 3C-1에서 보강했다. 3C-2는 이 방식을 그대로 사용하며 검사 제외나 기대값 완화를 하지 않는다.

원본 적용 전에는 최신 원본의 새 사본, 실제 배포 JAR, 같은 JDK/Windows/파일 저장 위치에서 다시 검증한다. 짧은 연결만 사용하는 독립 실행 경로도 따로 재현·분석한다. 검증용 원본 사본에서 실패하면 원본 적용을 중단하고 원인을 확인한다. FAQ 동작 검증을 이유로 이 위험을 해소된 것으로 표시하지 않는다.

## 2. H2/Flyway 버전 호환 경고

현재 H2 2.3.232에 대해 사용 중인 Flyway가 검증한 최신 H2는 2.2.224라는 경고를 낸다. 이 경고 자체와 FAQ 기능 테스트 결과는 구분한다. 3C-2에서 의존성 버전을 임의로 올리거나 DB를 변환하지 않는다.

원본 적용 전에 호환 조합을 검토하고, 버전 변경이 필요하면 별도 범위에서 전체 migration/재시작/발행본/이전 실행 파일과의 복구 검증을 진행한다. DB와 실행 파일을 반드시 짝으로 보존한다.

## 3. 3C-2까지의 허용 범위

- 3C-2 기능은 후기 V6 사본을 다시 복제한 FAQ DB에서만 실행한다.
- 원본 경로 차단 설정, schema V4~V6, 미완성 예전 V4의 격리를 유지한다.
- FAQ 사전 등록은 수동 후보 사전 SQL이며 schema migration이나 부팅 seed가 아니다.
- `docs/REACT_PHASE3C2_FAQ.md`에 기능 검증 결과와 현재 서버/기준점을 별도로 기록한다.

## 4. 3C-3 맛집 사본과 복구 호환

- FAQ V6 사본을 정상 종료한 상태에서 다시 복제한 `aica-phase3c3.mv.db`에만 V7을 적용한다. V7은 초안/발행본 주소 테이블 2개만 추가한다. V4~V6와 원본 경로 차단은 그대로 유지한다.
- V6→V7 검사는 이전 24개 테이블의 모든 컬럼, 기존 Flyway 이력, 재실행 0회 및 완전 재접속 후 값을 비교한다. 기존 V3→V6 실제 사본 검사도 별도로 계속 실행한다.
- H2/Flyway 호환 경고와 이전 짧은 파일 연결 현상의 원인이 해결됐다는 의미는 아니다. 원본 적용 전 최신 원본 사본·실제 JAR·동일 실행 환경에서 다시 검증해야 한다.
- **V7 DB에 이전 V6 JAR를 연결해 쓰지 않는다.** 이전 발행 처리는 새 주소 snapshot 복사를 알지 못한다. 롤백은 대응하는 V6 DB와 V6 JAR를 함께 복구한다. 최신 V7 작업을 보존하려면 중지 후 DB/JAR 쌍을 먼저 별도 보관한다.
- 주소가 남아 있는 맛집을 다른 유형으로 전환할 때는 명시적 비우기를 요구한다. 기존 Thymeleaf 요청의 주소 누락은 삭제가 아닌 보존이다.
- 추가 주소 데이터의 유형 조건은 PostService가 보장하며 DB에는 PK/FK/길이 제약을 둔다. 직접 SQL로 유형과 확장 행을 각각 바꾸는 운영 작업은 서비스 검증을 우회하므로 별도 점검이 필요하다.
- 이번 결과·사본 실행 주소·기준점은 `docs/REACT_PHASE3C3_RESTAURANT.md`에 기록한다.

## 5. 4A 블록 ID 변환과 이전 앱 호환

- 최신 V7 맛집 사본을 정상 종료해 복제한 `.cache/react-phase4a-data/aica-phase4a.mv.db` 계열에서만 V8을 검증한다. 원본 V3와 기존 V1~V7, 미완성 예전 V4 격리는 유지한다.
- V8은 Java Flyway migration이다. JSON 노드를 변환하되 모든 페이지의 JSON/ID 사전 검사를 마친 뒤 쓰기를 시작한다. H2 DDL의 암묵적 commit 특성 때문에 실패한 migration을 원본에서 수리하는 방식은 사용하지 않는다. 실패 사본을 보존하고 대응 기준점 DB/JAR에서 새 사본으로 재검증한다.
- V7 이전 앱은 새 블록 메타데이터를 저장 시 버릴 수 있으므로 V8 DB와 연결해 쓰지 않는다. 구버전으로 복구하려면 작업 전 V7 DB와 V7 JAR를 함께 복구한다.
- ID 없이 열린 이전 폼/클라이언트는 기존 페이지 저장을 거절하고 재조회를 요구한다. 현재 React/Thymeleaf는 모두 메타데이터를 보존한다.
- 서로 다른 과거 revision 사이의 블록 대응은 추측하지 않는다. 동일 snapshot임을 증명할 수 없는 경우 초안/발행본을 각각 식별하고 이후 재발행부터 같은 ID를 공유한다. 현재 페이지 1/65는 revision과 문서가 모두 동일해 같은 ID 집합을 부여했다.
- 삭제 ID 등록 기록은 페이지 삭제 후에도 남긴다. 직접 SQL로 JSON/등록 기록을 따로 수정하면 정합성 검사를 우회하므로 운영 도구에서 지원하지 않는다.
- H2/Flyway 호환 경고와 파일 연결 수명 위험은 기능 성공과 별도로 유지한다. 원본 적용은 4차 안정화 이후 최신 사본으로 다시 검증한다.

## 6. 4B Variation과 같은 V8 내 실행 파일 호환

- 4B는 최신 4A V8 사본을 새 `.cache/react-phase4b-data/` 계열로 복제한다. 새 migration/테이블/컬럼은 없고 V1~V8 파일은 변경하지 않는다.
- HERO centered는 기존 variation 필드의 개발자 등록 값이다. 이전 4A JAR는 이 값을 지원하지 않으므로 같은 V8이라는 이유만으로 실행 파일을 되돌리지 않는다. 복구 시 대응하는 DB/JAR 쌍을 사용한다.
- 등록 정의 조회 경로와 기존 PageService 검증을 공유한다. 운영자 자유 CSS/코드, 신규 콘텐츠 조건 필드는 추가하지 않는다.
- 기존 페이지 1·65의 시험 수정은 작업 후 복원했지만 정상 저장/발행의 revision·활동 이력 증가와 시험 블록 ID 폐기 기록은 사본에 남긴다.
- 원본 V3 적용 금지, H2/Flyway 호환 및 파일 연결 수명 위험은 계속 유지한다. 결과는 `REACT_PHASE4B_BLOCK_EDITOR.md`에 기록한다.

## 7. 4C-1 POSTS query와 같은 V8 내 JSON 계약

- `.cache/react-phase4c1-data/`의 새 V8 사본에만 작업한다. migration/분류 사전 추가 없이 sections_json의 optional sourceMode/query 필드를 확장한다. 원본 V3 SHA-256과 V1~V8 소스/기존 Flyway 이력은 유지한다.
- 예전 4B 실행 파일은 새 query 필드를 지원하지 않는다. 스키마 버전이 같더라도 DB와 JAR를 반드시 짝으로 복구한다. 작업 전/완료 후/중간 query 검증 사본은 각각 명시적으로 구분한다.
- 과거 클라이언트가 query 필드를 누락하면 저장을 거절한다. Thymeleaf의 현재 JS는 query를 보존한다. 직접 SQL이나 구버전 바이너리로 이 경로를 우회하지 않는다.
- 페이지 query와 콘텐츠 분류는 각각의 발행본을 사용한다. 향후 공개 사이트 연결 시 초안 PostService.list를 대신 호출하면 발행 경계가 깨지므로 PublishedPostQueryService를 재사용한다.
- 분류 사전 삭제/허용 주제 변경 기능을 만들 때는 JSON 블록의 참조 검사도 필요하다. 이번에는 그 관리 UI나 정책을 추가하지 않는다.
- 기존 H2/Flyway 경고와 파일 연결 수명 문제는 해결됐다고 간주하지 않는다. 원본 적용은 계속 금지한다. 결과·복구 기준점은 `REACT_PHASE4C1_POSTS_QUERY.md`에 기록한다.

## 8. 4C-2A manual 참조와 실행 파일 호환

- 새 `.cache/react-phase4c2a-data/` V8 사본에서만 작업했다. 새 migration/테이블/분류 사전은 없다. 원본 V3 체크섬과 기존 V1~V8 파일·Flyway 이력은 유지된다.
- manual에는 콘텐츠 ID 배열만 저장한다. 미발행·비공개·삭제·없는 ID도 설정에 남기고 공개 조회에서만 제외한다. 이후 참조 무결성 점검을 만들더라도 자동 삭제/순서 변경으로 처리하지 않는다.
- manual이 있던 블록에서 필드가 누락되는 저장은 거절한다. 명시적인 빈 배열이 선택 해제다. 현재 Thymeleaf JS는 이를 보존하지만 이전 4C-1 바이너리는 알지 못하므로 같은 V8 DB라도 JAR와 함께 복구해야 한다.
- 페이지의 선택 목록 snapshot과 콘텐츠 발행본 snapshot을 모두 사용한다. 향후 공개 사이트 연동 시 초안 목록 API를 대신 호출하지 않는다.
- 기존 H2/Flyway 경고와 파일 연결 수명 위험은 별도 유지한다. 이번 성공은 원본 migration 승인을 의미하지 않는다. 검증 범위·DB/JAR 기준점·복구 절차는 `REACT_PHASE4C2A_MANUAL_POSTS.md`와 해당 checkpoint의 RESTORE.md에 기록한다.

## 9. 4C-2B 원본 기반 블록 탐색

- `.cache/react-phase4c2b-data/`의 새 V8 사본에서만 검증했다. 새 DB/JSON 저장 구조와 migration은 없다. 원본 V3 체크섬 및 기존 Flyway 이력은 그대로다.
- 트리는 현재 페이지 초안의 메타데이터 투영이다. ID가 없거나 중복되면 탐색을 비활성화하고 저장 시 기존 식별 검사를 유지한다. migration을 대신해 제목/배열 순서로 ID를 추측하지 않는다.
- 삭제된 block URL을 다른 블록에 연결하지 않는다. 숨김은 편집 권한과 구분한다. 앞으로 템플릿/IA 연결을 만들 때도 이 원칙과 새 복제 ID 발급을 유지해야 한다.
- 현재 조회/선택만 바뀌므로 발행 처리는 기존과 같다. 그래도 복구는 기록된 DB/JAR 쌍을 사용한다. 원본 적용 금지와 H2/Flyway·파일 연결 수명 위험은 계속 유지한다. 결과는 `REACT_PHASE4C2B_BLOCK_NAVIGATION.md`에 기록한다.

## 10. 4D 공용 템플릿 (2026-09-27)

V9는 page_templates 테이블만 추가하며 기존 V1~V8 파일/원본 V3는 유지한다. V8 사본의 기존 모든 테이블/컬럼 fingerprint 보존과 재실행 0건을 검증했다. 복구는 V8+4C-2B 또는 V9+4D의 DB/JAR 쌍을 사용한다. 8091 완료 환경은 새 V8 백업 사본에 V9를 적용하고 검증 템플릿 두 개만 등록한 상태다. 템플릿은 실시간 연결이 아닌 복사 시작점이다. 템플릿 media/category/query/manual 참조의 수명 정책은 원본 적용 전 확인한다. H2/Flyway 호환 및 파일 연결 수명 위험을 이번 UI 기능 완료로 해소된 것으로 보지 않는다. 상세 근거와 복구 절차는 REACT_PHASE4D_TEMPLATES.md 및 4D 체크포인트 RESTORE.md에 기록한다.

## 11. 5A 공개 조회 API (2026-09-27)

실제 홈페이지가 아직 없다는 사용자 확인에 따라 공개 조회 계약만 구현했다. 원본 V3를 열어 migration하지 않으며 4D V9 백업의 새 사본만 사용한다. 추가 migration과 V1~V9 수정이 없다. 완료 환경은 작업 전 데이터와 동일하고 시험 발행/블록 변경은 별도 verified DB로 보관한다. 공개 트래픽의 운영 배치·CORS·캐시·시간대·파일 수명 정책, 실제 화면 E2E는 남아 있다. 특히 메뉴/공용 파일 메타데이터는 현 구조에서 즉시 설정이며 페이지/콘텐츠 발행 snapshot과 구분해야 한다. 공개 API는 초기부터 현재 공개 발행본에서 사용되는 미디어만 허용하고, 초안/숨김/템플릿/로고 설정만으로 파일을 공개하지 않는다. 기존 H2/Flyway 및 파일 연결 수명 위험과 원본 적용 금지는 유지한다. 상세 결과는 PHASE5A_RESULTS.md, 연결 계약은 PUBLIC_API_V1.md, 복구 쌍과 절차는 5A 체크포인트 RESTORE.md에 있다.


## 12. 5B-2A 확정 권한과 저장 보호 (2026-09-27)

원본 V3와 V1~V9 migration 파일은 보존한다. 새 DB migration은 없다. 신규 JAR는 확정된 SUPPORTER 초안 전용/ADMIN 기존 페이지 운영/SUPER_ADMIN 구조·영구 삭제 정책을 적용한다. 동일 V9라도 기존 JAR로 복구하면 권한 정책이 달라지므로 DB와 실행 파일·시간대 설정을 함께 복구하고 재검증해야 한다. offset API 표현은 Asia/Seoul로 기존 LocalDateTime을 해석한 것이며 기존 timestamp 데이터를 UTC로 변환한 것이 아니다.

활성/비활성 템플릿의 미디어 참조 보호는 완료했지만 버전 저장/이전 버전 미디어 보호는 5B-2B 범위다. 삭제 영향의 직접 URL 참조, 전역 설정 충돌 제어, 실제 공개 홈페이지 미연결은 남아 있다. H2/Flyway 경고와 파일 DB 연결 수명 문제, 원본 V3/검증 V9 차이는 계속 유지한다. 검증 테스트 통과를 원본 migration 승인이나 기술 위험 해결로 해석하지 않는다. 상세 결과·증거·복구 기준점은 PHASE5B2A_RESULTS.md에 기록한다.


## 13. 5B-2B-2 버전 이력 V10 (2026-09-27)

V10은 대상별 version 3개, version-media 3개, baseline 완료 마커 1개를 추가한다. 원본 V3와 기존 V1~V9는 유지한다. V3~V10 전체 경로·V9 사본 보존·별도 baseline 27개·버전 정리·복구와 재시작 검증을 완료했다. 최신 사본은 V10이며 원본과 실행 파일을 혼용하지 않는다.

과거 버전의 미디어 보호는 완료했다. 발행/baseline 무기한 보관의 용량 증가, 분류/컴포넌트 변경 후 과거 복구의 검증 실패, 실제 홈페이지 E2E 부재는 남는다. H2/Flyway 경고와 파일 DB 연결 수명 위험도 유지한다. DB와 JAR는 반드시 같은 기준점 쌍으로 복원한다. 상세 결과는 PHASE5B2B2_VERSION_HISTORY.md, 복구 절차는 5B-2B-2 checkpoint RESTORE.md에 있다.
