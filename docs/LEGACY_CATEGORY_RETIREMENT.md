# 레거시 카테고리 이관

기존 `categories`와 CATEGORY 참조를 현재 콘텐츠 유형·기수·주제 체계로 옮기는 단계. 후기(REVIEW)·FAQ는 이미 콘텐츠 유형이므로 이관 대상이 아니다.

## 조사 결과 (2026-10-01, 읽기 전용)

출처: 8095(V15 RC1)의 실제 V15 적용 중간본(V14) 사본. 표 지문 비교로 마지막 정상 종료 시점의 V15 운영 DB와 카테고리 관련 표가 모두 같음을 확인했고, 공개 API(익명 읽기)로 현재 값과도 일치했다.

| 카테고리 | 글(초안) | 발행본 | 메뉴 | POSTS 블록 | 버전 이력 |
|---|---|---|---|---|---|
| #1 공지사항 | 0 | 0 | CATEGORY #34·#65(둘 다 표시, 중복) | 없음 | 없음 |
| #2 교육 소식 | 1: #33 "아아"(GENERAL, 임시보관) | 0 | 없음 | 없음 | #33 기준본 스냅샷 1개(categoryId 2) |
| #33 카테고리1 | 0 | 0 | 없음 | 없음 | 없음 |

- 카테고리로 실제 걸러지는 POSTS 블록은 없다. 홈 "사관학교 소식"(초안·게시본), 인사교 소개 초안의 POSTS, 템플릿 2개는 모두 카테고리 방식에 카테고리가 없어 **발행된 전체 글, 최신순 6개**를 보여 준다. 인사교 소개 초안에는 쓰이지 않는 REVIEW 조건이 저장되어 있다.
- 공개 글은 #105(REVIEW) 1건. 모든 카테고리의 공개 목록은 비어 있다.

## 결정 (사용자, 2026-10-01)

1. 공지사항은 새 유형 없이 `GENERAL` + 주제 `GENERAL_NOTICE`.
2. 교육 소식은 `GENERAL_NEWS`를 만들지 않는다. #33은 자동 매핑 없이 GENERAL 그대로 두고 카테고리만 비운다.
3. "카테고리 없음 = 전체 글" 의미를 보존하기 위해 조건(query) 방식에 **전체 유형**을 둔다. 특정 유형으로 좁히지 않는다.
4. 인사교 소개 초안의 숨은 REVIEW 조건은 활성화하지 않고 전체 글로 바꾼다.
5. 카테고리 3개 행은 당장 지우지 않는다. 신규 사용 중단 → 참조 이관 → 관리 화면 숨김 → (참조와 버전 복원 호환이 정리된 뒤) 최종 삭제.

흐름: 신규 사용 중단 → POSTS를 의미 그대로 query로 전환 → 글의 category 값 제거 → 첫 사이트 구성 게시 → CATEGORY 메뉴 퇴출 → 관리 UI 숨김 → 아주 나중에 표·열·API 제거 검토.

## 코드 준비 (schema 변경 없음, V15 그대로)

| 항목 | 내용 |
|---|---|
| 전체 유형 | POSTS 조건의 `typeCode: null` = 모든 유형. 공개 조회는 기존 "카테고리 없음" 방식과 같은 SQL·정렬·개수. 전체 유형에서는 주제를 고를 수 없다(주제는 유형에 속함). 기수는 고를 수 있다 |
| 신규 사용 중단 | 글·POSTS 블록·페이지 템플릿에 카테고리를 **새로** 지정할 수 없다. 이미 가진 값은 그대로 두거나 비울 수 있다. 복제한 블록도 새 블록이라 카테고리를 가져갈 수 없다 |
| 카테고리 읽기 전용 | 추가·이름 변경·정렬·삭제 거부(React·기존 화면 모두). 목록·사용처 조회, 공개 `/posts?categoryId`, CATEGORY 메뉴는 그대로 |
| 버전 호환 | 이력은 옛 카테고리를 계속 보여 준다. 복원은 카테고리를 되살리지 않는다(현재 값과 같을 때만 유지) |
| 주제 추가 | `POST /api/admin/next/classifications/topics`(MANAGE_SITE, 추가만, 활동 이력 "주제 추가"). 등록된 사용 중 유형에만, 코드 `[A-Z][A-Z0-9_]{1,63}` 중복 불가, 같은 유형 안 같은 이름 불가. 관리 화면은 두지 않았다(UX 단계에서 정리). 이전 단계의 "어휘 추가는 운영자 기능이 아님" 방침을 추가 한 가지에 한해 바꾼 것이다 |
| 화면 | 새 POSTS 블록은 조건 방식 + 전체 유형으로 시작. 유형 선택에 "전체 유형". 기존 카테고리 방식 블록은 안내와 "같은 의미의 ‘전체 유형’ 조건으로 전환" 버튼(저장된 다른 조건은 깨우지 않음). 글 편집기는 카테고리가 있을 때만 보여 주고 "카테고리 해제"만 가능. 새 글은 카테고리를 받지 않는다. 콘텐츠 작업 사이드바에서 카테고리 항목을 뺐다 |

명칭·배치는 기능 완성 뒤 UX 단계에서 정리한다.

### 검증

- 서버 전체 229개 실행, 실패 0, 환경 조건 제외 6. `LegacyCategoryRetirementIntegrationTest`(5): 전체 유형 = 기존 방식 출력, 주제 거부 / 블록·템플릿 신규 카테고리 거부, 기존 값 유지 / 글 신규·변경 거부, 유지·해제, 복원 시 카테고리 미복원, 이력은 유지 / 카테고리 쓰기 거부, 읽기·공개 유지 / 주제 추가·중복·잘못된 유형·코드·권한·활동 이력
- 기존 시험 중 카테고리를 CMS로 만들거나 새 글에 지정하던 준비 코드는 "이미 저장된 레거시 데이터"로 넣도록 바꿨다(`LegacyCategories`). 카테고리 관리 시험은 읽기 전용 기대값으로, 템플릿 시험은 카테고리 없는 블록으로, 복원 시험은 "카테고리 미복원"으로 바꿨다.
- 프런트 79개(전환·숨은 조건 비활성·새 블록 기본값 추가), 타입 검사·빌드 통과. 미리보기(8081)에서 전환 버튼 → "조건으로 불러오기 · 전체 유형 · 최신순 · 6개" 확인.

## 실제 적용 순서 (계획)

1. 8095 V15 RC1 정상 종료 → 백업 → 새 JAR로 V15 RC2 교체(`swap-v12-jar.ps1`, schema 변경 없음) → 기동 → 세 역할·공개 API 동일 확인. 이 단계까지는 데이터 변경 없음.
2. 운영 데이터(승인 후): 주제 `GENERAL_NOTICE` 추가 → 홈 블록 전환·재게시 → 인사교 소개 초안 전환(게시하지 않음) → 템플릿 2개 전환 → #33 카테고리 해제.
3. 되돌리기: 1단계 뒤에는 V15 RC1 선택만으로 된다. **2단계(운영 데이터 전환) 뒤에는 옛 JAR 단순 rollback이 아니라 전환 직전 DB 백업 복원이 필요하다.** 옛 JAR는 전환된 "전체 유형" 블록을 읽을 수는 있어도 저장하지 못한다. 그래서 2단계 전에는 반드시 정상 종료 후 최신 백업을 새로 확보한다.
4. CATEGORY 메뉴 퇴출은 첫 구성 게시 때, 카테고리 행 삭제는 그 뒤 별도 단계에서 한다.

### 되돌리기 절차 (전환 뒤)

옛 JAR 단순 rollback으로는 부족하다. 전환 직전 DB 백업을 복원해야 한다.

1. 8095 정상 종료(STOP.cmd).
2. `.cache/v15-release/V15-RC1-20260930/runtime/db/aica-local.mv.db`(RC1·RC2가 함께 쓰는 DB)를 `aica-local.before-category-conversion-20261001-stopped-1790784063899.mv.db`로 덮어쓴다. 복원 뒤 해시가 `60e1767d…`인지 확인한다.
3. 필요한 JAR를 선택한다: 새 JAR 유지(V15 RC2) 또는 옛 JAR(V15 RC1, `select-v12-runtime.ps1`). 복원된 DB는 전환 전 상태라 두 JAR 모두 편집까지 가능하다.
4. 기동 후 세 역할·공개 API를 확인한다.

1단계만 되돌릴 때(전환 전)는 V15 RC1 선택만으로 된다(`aica-local.before-V15RC2-20261001-...` 백업은 보험).

## 후속 과제

- **정식 기수·주제 관리 UI**: 이번에 넣은 `POST /api/admin/next/classifications/topics`(주제 추가만)는 카테고리 퇴출을 위한 **과도기 수단**이다. 향후 기수·주제 관리 화면(추가·이름·순서·비활성화, 게시본 이름 스냅샷과 기존 배정 보호)을 만들 때 그 기능에 흡수하고 이 단독 API는 정리한다.
- CATEGORY 메뉴 퇴출: 첫 사이트 구성 게시 때(공지사항 영역은 IA 입력 단계에서 `GENERAL` + `GENERAL_NOTICE` 조건으로 구성).
- 카테고리 행·관리 화면·공개 `categoryId` 계약 정리: 참조와 버전 복원 호환이 모두 정리된 뒤 별도 단계.
